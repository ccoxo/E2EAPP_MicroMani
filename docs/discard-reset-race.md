# 丢弃与回工作原点竞态（2026-09-18）

现场日志 `backend/runtime/logs/appstation-m0-20260918_173152.log` 显示：

- 17:45:53.514 前端已显示“已丢弃，等待复位”，但后端丢弃请求尚未返回。
- 17:45:54.392 回工作原点请求开始，涉及 Roll 约 47.7° 的运动。HAL 普通命令线程会等待回原点完成。
- 17:45:59.648 `teleop.native.stop` 应答超时，发布耗时 0.5 ms、等待 5001.3 ms、协程恢复 0.1 ms。该停止请求属于丢弃收尾，排在先到达的回原点请求之后。
- 停止请求超时导致 DDS 控制通道隔离及急停，回原点以“motion command cancelled by emergency stop”结束。

前端原先不等待丢弃 API 成功就进入 resetting；后端原先先清理录制队列、再停止遥操作。这使尚未结束的丢弃与回原点重叠。此次不是最初的 `control.lease` 心跳先超时，也没有证据证明是 Omega 物理拔线。

## 修复

- 新增 discarding 状态及“丢弃中，等待遥操作停止”提示；只有丢弃 API 成功才进入复位等待并记录丢弃历史。
- 丢弃进行中拒绝重复丢弃、结束和录制页回工作原点。丢弃失败进入待核验状态，不显示丢弃成功。
- 后端先停止遥操作，再清理待丢弃数据；丢弃期间回原点 API 拒绝执行，避免仅依赖按钮禁用。
- 保留原 DDS 超时、租约、急停和控制通道隔离机制；没有修改 C++ HAL 或速度参数。

## 验证边界

离线测试覆盖延迟丢弃应答、重复点击、回原点拦截、失败保留、停止早于清理及 API 完成后恢复。前端类型检查通过。需要重启后端并加载更新的前端后，验证真实丢弃及回原点流程；未自动操纵设备。该修复针对本次竞态，不代表此前所有 DDS 超时均已确定原因。
