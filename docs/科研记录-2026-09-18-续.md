### 2. 图像标准差异常

发现单段图像标准差为 0，汇总标准差也明显偏小。安装版本的 LeRobot 视频统计对 uint8 像素直接计算平方，产生溢出，随后方差被截断为 0。离线最小样例中，像素值 0 和 255 的总体标准差应为 127.5，原统计路径得到 0。

处理分为两个部分：

- **后续采集：**在独立编码进程内将统计输入转为 float64 后计算，不修改安装包，也不改变原图像编码数据。
- **已有数据：**从已保存的 MP4 解码 RGB，遍历全部帧、沿用空间下采样并重算图像统计，输出到 `E:\data group\micro_assembly_v5_stats_fixed`。保留原目录。

修复副本三路归一化 RGB 标准差约为 0.27～0.31。对副本的 15 个视频及 5 个数值文件进行 SHA-256 核对，均与原文件一致；非图像统计及其他 episode 元数据未改动。解码后像素与压缩前像素可能略有差异，因此重算值不应被解释为逐位还原了原始相机统计。

### 3. 保存末帧的夹爪动作异常

episode 1 的最后一帧（`frame_index=822`，全局 `index=1811`，27.4 s）出现操作者左侧夹爪目标 `action[6]` 从约 2.22857 变为 1.02，而该侧观测夹爪状态约为 2.24314 且保持不变。

代码路径表明：正常保存先停止遥操作，再处理排队尾帧；尾帧原先仍读取实时动作状态，可能读到停止后的重置值。修复为停止前深拷贝动作状态，排队尾帧读取该快照，新 episode 开始时清空快照。保留先停设备再完成写入的顺序。

已有异常帧真实动作不能仅凭邻帧确定，因此未插值覆盖。修复副本的 `meta/quality_review.json` 标记该帧待核验，建议训练时排除该帧及包含它的序列窗口。此标记不会自动被训练加载器应用。

## 三、结束采集时的安全租约故障与质量报告问题

### 1. 17:23:40 故障

现场日志：`backend/runtime/logs/appstation-m0-20260918_172016.log`。

用户描述为点击结束采集后没有质量报告弹窗，界面仍在，但遥操作失连。日志最先出现 `DDS control reply timed out: control.lease`，随后急停请求也未得到应答，前端开始约每秒一次断开、重连。相机日志仍持续输出，Omega 日志仍显示物理连接，故不能直接归因于设备拔线。

已确定的连锁机制：DDS 控制应答超时触发后端通道隔离，该实例要求重启；前端却仍自动重连，新租约申请持续失败。修复为后端发送 `restartRequired` 标记，前端停止自动重连并显示重启后端及显式安全确认提示。增加 DDS 超时请求编号、发布耗时、等待耗时和协程恢复耗时，以区分后续故障阶段。

**限制：**这一轮最初的 `control.lease` 应答超时根因尚未确定。停止重连只修复错误恢复表现，不能称为消除了所有租约超时。

### 2. 结束按钮跳过质量报告

离线回归复现：在 recording 状态直接点击结束，会进入 finishing，跳过保存和质量报告。现改为先保存当前片段，进入报告审核，接受报告后再结束；保存失败不继续 finalize，保留会话待处理。

该流程缺陷与现场“不弹报告”现象相符，但尚无证据证明它导致了上述首次 DDS 超时，应分别记录。

## 四、丢弃后回工作原点引发停控

### 1. 现场时序

日志：`backend/runtime/logs/appstation-m0-20260918_173152.log`。

| 时间 | 事件 |
| --- | --- |
| 17:45:53.514 | 前端显示 Episode #4 已丢弃、等待复位 |
| 17:45:54.392 | 回工作原点请求开始；其中 Roll 需运动约 47.7° |
| 17:45:59.648 | `teleop.native.stop` 应答超时；发布 0.5 ms，等待 5001.3 ms，协程恢复 0.1 ms |
| 随后 | DDS 通道隔离及急停，回原点返回“motion command cancelled by emergency stop” |

这次首个超时是停止遥操作命令，并非心跳先超时。前端原先不等待丢弃 API 成功就开放复位；后端原先先清理录制队列再停止遥操作。与此同时，HAL 普通命令线程等待回原点运动完成。代码与日志共同支持如下时序：回原点先进入执行，丢弃收尾的停止命令排在其后，等待超过 5 秒后触发保护，导致回原点被取消。

### 2. 修复措施

1. 前端新增 discarding 状态，显示“丢弃中，等待遥操作停止”；API 成功后才显示丢弃完成、更新历史并开放复位。
2. 丢弃期间拒绝重复丢弃、结束和录制页回原点；失败进入待核验状态，不提前宣告成功。
3. 后端先停止遥操作，再清理待丢弃数据；只有处理完毕才进入复位等待。
4. 后端回原点接口也检查丢弃是否进行中，避免只靠前端按钮限制。

未修改 C++ HAL、回原点速度或安全超时阈值。此次离线修复针对已识别的竞态；修改后仍需实机执行丢弃、等待完成、回原点及下一段采集验证。
